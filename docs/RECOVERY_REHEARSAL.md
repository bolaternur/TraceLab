# Проверка восстановления Iznera

## Воспроизводимая локальная проверка

Из корня репозитория:

```powershell
node scripts/verify-isolated-recovery.mjs
```

Скрипт использует локальные `DATABASE_URL`, `DATABASE_MIGRATION_URL` и установленный PostgreSQL (`PG_BIN`, либо локальная установка проекта). Значения подключений не выводятся. Миграционная роль должна уметь создавать базы, runtime-роль остаётся ограниченной.

Проверка создаёт две новые базы с уникальным префиксом `tracelab_unified_test_recovery_` и отдельные каталоги `.data/recovery-rehearsals/<идентификатор>/`. Она не читает материалы настоящих команд, не заменяет существующую базу, не меняет рабочий `STORAGE_ROOT` и ничего не удаляет.

Сценарий:

1. Создать вымышленные аккаунты и команду через серверные функции приложения.
2. Сохранить фотографию, приватную миниатюру, авторскую подпись и неизменяемый JSON-отчёт через настоящие media/report pipelines.
3. После завершения записывающего процесса сделать PostgreSQL dump и копию приватных файлов. Записать размеры и SHA-256 каждого объекта.
4. Восстановить dump в новую базу, вернуть ограниченные runtime grants, скопировать файлы в новый каталог.
5. Прочитать запись, исходную фотографию, миниатюру и отчёт через функции приложения. Проверить совпадение байтов, автора и подписи; проверить отказ чужому пользователю.

Результат сохраняется в `recovery-result.json`. Тестовые базы и файлы остаются для проверки. Успешный прогон 1 ноября 2026 года: три приватных объекта восстановлены, контрольные суммы и запреты доступа совпали.

## Граница результата

Это практическое восстановление **локальной базы вместе с локальными файлами на изолированных данных**. Оно не подтверждает backup production, Supabase, непрерывные записи во время копирования, point-in-time recovery, внешнее шифрование, хранение ключей или исполнение сроков удаления резервных копий.

Для реальной эксплуатации оператор должен назначить срок хранения, защищённое место для копий и секретов, остановить записи/очереди на время согласованного снимка либо использовать согласованный snapshot-механизм. База и object storage восстанавливаются парой в отдельной среде. Проверка должна завершиться до переключения production на восстановленную среду. Этот тестовый скрипт намеренно не содержит команды замены рабочей базы.

Локальная ZIP-копия офлайн-черновиков и JSON из настроек аккаунта решают другие задачи; они не заменяют полный backup сервера. См. [фактический жизненный цикл данных](DATA_LIFECYCLE_STATUS.md).
