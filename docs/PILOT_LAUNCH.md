# Запуск TraceLab для первых команд

Проверка: 28 октября 2026 года. Рабочая копия: `C:/Users/User/projects/TraceLab-web`. Это инструкция подготовки и приёмки, а не подтверждение уже опубликованного сервиса.

Первые четыре шага для владельца:

1. Создать аккаунты Render, Supabase и Resend; выбрать домен отправки писем. Сайт сначала может открываться по выданному Render HTTPS-адресу.
2. Создать ресурсы по разделу ниже и сохранить ключи в secret settings сервера. В чат передаются только названия ресурсов/домен, без ключей и паролей.
3. Выпустить серверную версию и пройти проверку двумя разными аккаунтами. Успешной главной страницы недостаточно: нужны письма, код команды, общие записи и приватные файлы.
4. После приёмки дать нескольким командам публичный адрес; ответственный каждой команды создаёт её собственный код и передаёт только своим участникам.

## Что работает локально и что нужно для интернета

`http://localhost:3000` открывает сервер только на компьютере владельца. Команды с других устройств должны получить один публичный HTTPS-адрес **полного root Next.js приложения**. GitHub Pages из `.github/workflows/presentation-pages.yml` публикует презентацию и локальное демо; регистрации, общей базы и приватных API там нет.

Для пилота нужны четыре настроенных ресурса:

| Ресурс | Что требуется | Текущая граница |
| --- | --- | --- |
| Сервер приложения | Постоянный Node.js runtime, HTTPS и точный публичный `APP_URL` | Хостинг и домен владельцем ещё не выбраны/не подключены |
| PostgreSQL | Отдельная база пилота; ограниченная роль приложения и отдельный владелец миграций | Локальная база существует; её адрес не работает на чужом хостинге |
| Письма | Resend, проверенный домен отправителя и реальная доставка | Локальные тестовые письма не доставляются участникам |
| Файлы | Private Supabase bucket либо проверенный постоянный приватный диск | Временный диск хостинга не подходит для фото/моделей |

Ни аккаунты провайдеров, ни DNS, ни публичное размещение этой инструкцией не создаются. Названия и ключи добавляются в серверные secret settings; реальные значения не отправляются в чат и не коммитятся.

## Предлагаемый первый путь: Render + Supabase + Resend

Для этого проекта предлагается **Render Web Service** с Node.js, Supabase для PostgreSQL/приватных файлов и Resend для писем. Это выбранное направление подготовки, а не уже оплаченный или опубликованный сервис.

1. В [Render](https://dashboard.render.com/) создать **Web Service**, подключить репозиторий TraceLab, выбрать корень проекта. Настройки: Language `Node`, Build Command `npm ci && npm run build`, Start Command `npm start -- --hostname 0.0.0.0`, Health Check Path `/api/health`, `NODE_VERSION=22.x`. Порт берётся из серверного `PORT`. Render выдаёт `https://имя.onrender.com`; этот адрес записывается в `APP_URL`. Поскольку платформа завершает TLS перед Node-сервером, проверить доверенную передачу Host/proto/IP и задать `TRUST_PROXY=true` по контракту ниже. [Next.js на Render](https://render.com/docs/deploy-nextjs-app), [порты и HTTPS](https://render.com/docs/web-services), [версия Node](https://render.com/docs/node-version).
2. Для командного пилота выбрать постоянный работающий compute после согласования стоимости владельцем. Free Render засыпает после 15 минут простоя; локальные файлы теряются при перезапуске/выпуске. Private Supabase Storage поэтому используется вместо диска приложения. Текущие лимиты и стоимость проверяются в панели перед покупкой. [Ограничения Free](https://render.com/docs/free).
3. В [Supabase](https://supabase.com/) создать отдельный проект пилота. В SQL Editor создать отдельную login role `tracelab_runtime` с `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS` и случайным паролем, который хранится только в secret settings. Runtime не получает членство в owner role. Подробности ролей: [Postgres roles](https://supabase.com/docs/guides/database/postgres/roles).
4. В **Connect** взять Session pooler URL для runtime, если сервер использует IPv4. Пользователь для custom role имеет форму `tracelab_runtime.<project-ref>`; поэтому задать `DATABASE_RUNTIME_ROLE=tracelab_runtime`. Миграции выполняются через отдельный owner connection, предпочтительно Direct connection из доверенной release-среды с подходящей сетью. Использовать рекомендованную провайдером проверку TLS-сертификата. [Типы соединений Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres).
5. В Supabase Storage создать private bucket и настроить три `SUPABASE_*` переменные из таблицы ниже. В Resend подтвердить свой домен отправителя, настроить ключ и `MAIL_FROM`. Адрес `onrender.com` позволяет открыть сайт, но не заменяет домен, которым владелец управляет для отправки писем.
6. Применить миграции отдельным release job, выполнить preflight, включить сервер и пройти приёмку ниже. Проверить реальную загрузку безличных файлов у границ **15 MiB для фото / 25 MiB для GLB**: пригодность конкретного хостинга подтверждается этим тестом, а не только настройкой приложения.

## Окружение сервера

Настроить эти переменные на выбранном сервере:

| Имя | Требование |
| --- | --- |
| `NODE_ENV` | `production` |
| `APP_URL` | Точный публичный HTTPS origin без пути; совпадает с адресом браузера |
| `TRUST_PROXY` | `true` для проверенного HTTPS reverse proxy; не включать при прямом недоверенном доступе |
| `DATABASE_URL` | Роль без владения таблицами, `SUPERUSER`, `BYPASSRLS`, `CREATEDB` и `CREATEROLE` |
| `DATABASE_RUNTIME_ROLE` | Фактическая PostgreSQL role, например `tracelab_runtime`, если login URL pooler содержит суффикс проекта |
| `SECRETS_ENCRYPTION_KEY` | Постоянный случайный секрет, минимум 32 символа; сохранить защищённую резервную копию |
| `CRON_SECRET` | Отдельный случайный секрет для доверенного планировщика |
| `MAIL_TRANSPORT` | `resend` |
| `MAIL_ENABLE_EXTERNAL_DELIVERY` | `true` после подключения провайдера |
| `MAIL_PREVIEW_ENABLED` | `false` |
| `MAIL_FROM` | Адрес проверенного домена Resend |
| `RESEND_API_KEY` | Серверный ключ отправки; не `NEXT_PUBLIC_*` |
| `STORAGE_PROVIDER` | `supabase` для подготовленного облачного адаптера |
| `SUPABASE_URL` | HTTPS origin своего проекта |
| `SUPABASE_SERVICE_ROLE_KEY` | Только серверный секрет |
| `SUPABASE_STORAGE_BUCKET` | Имя **private** bucket |
| `AI_PROVIDER` | `disabled` для первого пилота |
| `ENABLE_DEV_SIMULATOR`, `DEV_AUTH_BYPASS` | Не включать |

`DATABASE_MIGRATION_URL` нужен отдельному доверенному release job для миграций, а не постоянно работающему веб-процессу. Его роль должна отличаться от роли `DATABASE_URL`. При managed PostgreSQL используйте TLS и правила соединения своего провайдера.

Для local storage вместо Supabase задаются `STORAGE_PROVIDER=local` и приватный постоянный `STORAGE_ROOT`. Перед этим отдельно подтверждаются постоянство тома, права, свободное место, резервирование и восстановление. Смена провайдера не переносит существующие объекты.

`TRUST_PROXY=true` допускается только за доверенным HTTPS proxy с закрытым прямым доступом к приложению. `Host` должен совпадать с host из `APP_URL`, `X-Forwarded-Proto` — быть одним значением `https`, а переданный `X-Forwarded-Host` — совпадать с тем же host. Origin браузера обязателен и должен точно совпасть с `APP_URL`. Этот контракт проверен на локальном production-сервере с моделью TLS-прокси; реальный выпуск проверяется отдельно.

Для сетевого ограничения регистраций `TRUST_PROXY_HOPS=1` выбирает последний доверенный адрес в `X-Forwarded-For`, а не произвольный первый адрес от клиента. Если цепочка сложнее, число доверенных proxy (1–5) устанавливается только после проверки её фактического устройства. Адреса проверяются как IP; ошибочная настройка использует общий ограниченный bucket. Без `TRUST_PROXY` все регистрации делят общий bucket. [Правило выбора доверенного адреса](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For#selecting_an_ip_address).

Для HTTPS proxy отдельно проверить signup POST: публичный `Origin` должен точно совпадать с `APP_URL`, `Host` — с его host/port, forwarded proto — с `https`; если передан forwarded host, он также совпадает. Внутренний HTTP-hop не меняет публичный origin. Несовпадающие/cross-site запросы должны получить отказ; не исправлять это отключением проверки Origin.

Подробности: [Resend](account-mail-setup.md) и [Storage](EXTERNAL_SERVICES.md). Resend требует проверки своего домена; private bucket обязателен для командных материалов. [Документация Resend](https://resend.com/docs/dashboard/domains/introduction), [Supabase private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals).

## Сборка и выпуск

Команды запускаются из корня актуального репозитория. Перед первым выпуском создаётся **пустая база пилота**, без `db:seed`. Старые личные базы и браузерные проекты не заменяются.

```sh
npm ci
npm run db:migrate
node scripts/check-migrations.mjs
npm run lint
npm run typecheck
npm test
npm run test:static
node --test tests/pilot-preflight.node.test.mjs
npm run build
```

`npm run test:db` выполняется отдельно только против `tracelab_unified_*` development/test базы; не против пилотной базы с материалами команд. CI создаёт отдельную `tracelab_unified_test_ci`, применяет зарегистрированные миграции и использует ограниченную runtime role. Старые тесты с Orion seed не являются приёмкой нового приложения.

После миграций убрать owner connection из окружения веб-процесса. Запуск за HTTPS reverse proxy:

```sh
npm start -- --hostname 127.0.0.1 --port 3000
```

Это команда для сервера с proxy на том же узле. На managed-хостинге используются его параметры внутреннего порта/слушателя. Не запускайте публичный пилот через `next dev`. Self-hosting требует proxy для HTTPS, ограничения входящих запросов и корректной передачи origin; [документация Next.js](https://nextjs.org/docs/app/guides/self-hosting).

Проверка конфигурации ничего не отправляет в Resend/Storage:

```sh
node scripts/pilot-preflight.mjs
node scripts/pilot-preflight.mjs --check-db
```

Первая команда анализирует только окружение; вторая дополнительно выполняет read-only запросы через `DATABASE_URL` и проверяет привилегии роли/наличие unified-таблиц. Для явной локальной диагностики можно добавить `--env-file=.env.local`; ожидаемый результат текущего development окружения — **пилот ещё не настроен**. `--json` возвращает только статусы и имена настроек, без ключей/connection strings. Успех этих команд не означает, что письма доставляются или что bucket проверен настоящей загрузкой.

Открыть `https://ваш-домен/api/health`: ожидается HTTP 200 и `{"ok":true}`. Этот endpoint проверяет соединение с БД; он не проверяет почту, файлы, права всех команд или восстановление.

Локальная репетиция CI 28.10 выполнена с нуля: создана отдельная случайно названная `tracelab_unified_test_ci_verify_*` база и ограниченная роль; применены все 13 зарегистрированных миграций, все хеши совпали, **56/56 DB-тестов в 10 suites прошли**. После проверки удалены только созданные этой репетицией база и роль. Это не запуск GitHub Actions и не проверка облачных провайдеров.

## Приёмка двумя участниками до выдачи адреса командам

1. Участник A регистрируется своим адресом, получает настоящее письмо, подтверждает почту и входит. Создаёт пустую команду A и первый проект. После reload название и проект остаются.
2. Ответственный A создаёт код своей команды и передаёт его только участникам этой команды. Код даёт членство; хранить его как приглашение, а не публиковать на общей странице. В настройках проверить срок, лимит и отзыв кода. Существующие одноразовые приглашения также должны работать.
3. В другом браузере/профиле участник B регистрируется с другим адресом, подтверждает его и вводит код A. У B открывается именно команда A, с общей историей. Повторное присоединение уже состоящего участника не создаёт второе членство.
4. A сохраняет безличное тестовое фото и подпись. B открывает/обновляет общую рабочую область, видит запись и добавляет собственное испытание с объяснением. A видит испытание. Авторство не переписывается другим участником; спорная правка сохраняется отдельным вариантом, а не уничтожает первый текст.
5. Присоединить к отдельной команде C ещё один тестовый аккаунт. Прямые URL записей, файлов и PDF из A должны отказать C. После отзыва членства B доступ к новым запросам A исчезает. Не проверять это на реальных личных файлах.
6. Проверить неверный, отозванный, исчерпанный и просроченный код; отсутствие повышения роли студентом. Код команды A не должен давать доступ к C.
7. Загрузить фото и маленький GLB; открыть миниатюру/модель. Сформировать инженерный PDF, скачать и проверить страницы. После перезапуска приложения файлы и записи доступны прежним участникам.
8. Сохранить фото в офлайн-очередь, перезагрузить, затем отправить. До подтверждения сервера локальная копия остаётся; повторная отправка не создаёт дубль. Смена аккаунта не отправляет чужую очередь.
9. На собственном тестовом адресе проверить восстановление пароля и прекращение прежних сеансов. Проверить доставку и retry с временной ошибкой почтового провайдера; журналы не должны содержать токены и тексты приватных записей.

Общая база уже позволяет разным аккаунтам работать над одними материалами. Перед пилотом отдельно проверить фактическое обновление второго браузера: не обещать Google Docs-подобное редактирование одновременно, presence или мгновенную синхронизацию, если соответствующий путь ещё не проверен.

## Резервирование и условия приглашения первых команд

Перед первой реальной загрузкой сохранить восстановимую пару **БД + private object storage**, а также отдельно защищённую копию encryption key. Проверить восстановление в изолированной среде по контрольным суммам файлов и связям БД; простого совпадения количества строк недостаточно. `scripts/verify-local-backup.mjs` сейчас проверяет только локальную БД, не файлы и не облачную резервную копию.

Для пилота назначить ответственного за доставку писем, недоступность сервиса, возврат локальных черновиков и доступ участников. Установить согласованный порядок обработки персональных данных и контактов команд, особенно несовершеннолетних. Изменение email, удаление аккаунта и физическое удаление команды пока нельзя обещать как готовые пользовательские операции.

Почтовый outbox сохраняет сообщения и делает ограниченные попытки. Подготовлен `POST /api/account/mail-dispatch`: доверенный планировщик раз в минуту вызывает его с `Authorization: Bearer <CRON_SECRET>` из серверного секрета. Endpoint не подключает планировщик автоматически. Настоящий ключ не вставляется в URL, GitHub workflow text или открытые журналы. Ответ содержит только счётчики `processed`, `sent`, `failed`, `exhausted`; HTTP 503 при отсутствии Resend, ошибке или исчерпании попыток требует внимания оператора. Максимум три попытки доставки на сообщение остаётся прежним. API не раскрывает адреса/письма/ссылки и не превращает fixture-тест в подтверждение живой доставки.

Планировщик и оповещение оператора на 503 необходимо действительно настроить до unattended-пилота. Контроль готовности: [матрица](IMPLEMENTATION_MATRIX.md), [проверки](VERIFICATION_2026-10-27.md). Полная a11y/physical-device/performance и combined restore приёмка остаются отдельными пунктами.
